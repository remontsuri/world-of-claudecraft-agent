# LEARNING — контур самоулучшения агента

Дата: 2026-09-18. Линия: `woof-ts`. Код: `src/learn/` (`objective.ts`, `tune.ts`),
пороги: `src/policy/params.ts`, артефакты: `learning/`.

## Что это и чем не является

Агент играет сам и сам подбирает себе пороги — но **не переписывает свой код и не
меняет целевую функцию по ходу**. Контур обучения:

1. объявляет целевую функцию и сплит сидов **до** первого измерения;
2. предлагает значения из объявленной сетки (`PARAM_SPECS`: def ± step, ± 2·step,
   в пределах `[min, max]`);
3. прогоняет каждого кандидата **отдельным процессом** (`WOOF_PARAMS=<file>`), потому что
   `PARAMS` читается при импорте модуля: статические импорты ESM поднимаются до разбора argv,
   поэтому поменять пороги внутри процесса нельзя в принципе. Побочный плюс — падение
   кандидата не роняет тюнинг;
4. принимает изменение, только если вырос средний скор на train-сидах;
5. проверяет итоговый набор на val-сидах, которые в подборе не участвовали;
6. пишет каждое измерение (и каждый отказ) в append-only историю.

Это поиск по объявленной таблице, а не «ИИ переписывает себя»: интерпретацию результата
и решение о применении делает человек, а отказ от гипотезы сохраняется так же, как принятие.

## Целевая функция (объявлена до измерения)

```
score = 100·quests_done + 5·kills − 10·deaths + 25·(level−1)
        + 20·[first_turn_in_step ≤ 40] − 0.001·world_steps
```

Смысл весов: квест важнее фарма, фарм важнее суеты; смерть — штраф; ранняя сдача — бонус;
расход шагов мира — штраф за эффективность (иначе подбор находит «бег по кругу ради убийств»).
Один сданный квест (100) примерно уравновешивает 20 убийств (5·20), поэтому «фармить вместо
квестов» выгодно только при большом перевесе.

**Менять веса после измерения запрещено.** Новая цель = новая гипотеза, новая запись в
`learning/history.jsonl` и строка в `PROGRESS-<дата>.md`.

## Запуск

```bash
bash tools/setup_game.sh && npm run build
node dist/tune.mjs --steps 150 --train-seeds 42,43 --val-seeds 44 --groups combat,survival
# через бридж (мир за env-сервером игры):
node dist/tune.mjs --steps 120 --transport ndjson --train-seeds 42 --val-seeds 44 --groups quest
```

Опции: `--rounds`, `--candidates-per-param` (1 = ±step, 2 = ±step и ±2·step),
`--budget-seconds` (по исчерпании фиксируется лучшее из проверенного, а не «оптимальное»),
`--min-delta` (порог принятия; **по умолчанию 1.0** — при 0 контур принимал шум: наблюдалось
принятие кандидата с приростом +0.05), `--out`.

Контур сам объявляет слабые места до измерения и пишет их в отчёт и `best.json`
(`warnings`): один train-сид, меньше трёх val-сидов, бюджет короче 100 решений. Это не
блокирует запуск, но делает результат интерпретируемым: «улучшение на одном сиде» и
«улучшение» — разные утверждения.

Стоимость считается и печатается до старта: `параметры × значения × train-сиды × ~время прогона`.
Прогон на 150 решений — десятки секунд, поэтому тюнинг всегда бюджетирован.

## Артефакты

| Файл | Что |
|---|---|
| `learning/history.jsonl` | append-only: каждое измерение (baseline, кандидат, принят/отклонён, скоры по сидам, ошибки прогонов) |
| `learning/best.json` | принятый набор порогов, дифф от базовых, train/val скоры, условия (транспорт, шаги, сиды), длительность |
| `learning/last_report.md` | датированный отчёт: цель, условия, результат, предупреждения, **вердикт по val**, принятые пороги, команда воспроизведения |
| `evidence/tuning/` | evidence-файлы отдельных прогонов (не коммитятся: это черновики, см. `.gitignore`) |

Применить найденное в обычном прогоне:

```bash
WOOF_PARAMS=learning/best.json node dist/run.mjs --seed 42 --steps 150 --quiet
```

Прогон печатает дифф порогов **до** измерения (`[WoOF] пороги: … levelDeltaMax: 1→0`) и
кладёт `params` + `paramsDiff` в evidence — иначе результат нельзя атрибутировать настройке.

## Прогоны контура (2026-09-18) и два вывода, которые важнее результата

### Запуск 1: один val-сид — это шум

`--steps 60 --train-seeds 42 --val-seeds 44 --groups quest`, порог принятия тогда был 0.

| Что | train (сид 42) | val (сид 44) |
|---|---|---|
| базовые пороги | −71.56 | −14.02 |
| `levelDeltaMax: 1 → 0` (принято) | **116.52** | −13.95 |
| `levelDeltaMax: 1 → 2`, `giverFailExhaust: 3 → 2 / 4` | без прироста (отказ) | — |

Прирост на одном val-сиде (−14.02 → −13.95) — 0.07 пункта, то есть ничего. Вывод:
**val-сплит меньше трёх сидов не измеряет переобучение.**

### Запуск 2: три val-сида, порог принятия 1.0 (текущие артефакты в `learning/`)

`node dist/tune.mjs --steps 60 --train-seeds 42 --val-seeds 43,44,45 --groups quest`

| Что | train (42) | val (43, 44, 45) |
|---|---|---|
| базовые пороги | −71.56 | −3.76 |
| `levelDeltaMax: 1 → 0` (**принято**, отклонены `→2`, `giverFailExhaust →2/4`) | **116.52** | **72.95** |

Вердикт контура: «на val-сидах набор не хуже базового — можно применять с оговоркой про
размер сплита». Предупреждения в отчёте: один train-сид, бюджет 60 решений.
Длительность 182 с, 11 прогонов.

**Вывод 1: скор зависит от бюджета решений.** Тот же `levelDeltaMax=0` на 150 решениях
даёт `kills=0, world_steps=10684, quests_done=1` — хуже базового (`24 / 4323 / 2`).
На короткой дистанции осторожность выигрывает (агент не ввязывается в бой и не умирает),
на длинной — проигрывает. Значит: подбирать на том же `--steps`, на котором объявлена
приёмка (`--steps` пишется в `best.json` и в отчёт), и не смешивать бюджеты в одной истории.

**Вывод 2: принятие «улучшения» на +0.05 — это принятие шума.** Порог принятия поднят
с 0 до 1.0 пункта скора (меньше веса одного убийства, больше дрожания прогонов). После
этого кандидат `searchActions: 12 → 10` с приростом +0.05 был отклонён — тот же прогон,
та же цель, другое решение. Изменение порога принятия зафиксировано здесь и в
`../knowledge/woof-ts.md` до того, как использовано: это правило поиска, а не целевая
функция (веса не двигались).

### Что при этом поймал гейт

Полный `check_all.sh` дважды падал на шаге 7, и оба раза по делу:

1. проверка искала строку `целевая функция (объявлена до измерения)` в нижнем регистре,
   а в отчёте она с заглавной — `grep -i` в локали C не складывает байты кириллицы.
   Исправлено на литеральное совпадение (`grep -qF`).
2. шаг не проверял, что **страж переобучения согласован с числами**. Добавлена проверка:
   если `valMean < baselineValMean`, в отчёте обязан быть вердикт «ПЕРЕОБУЧЕНИЕ», и наоборот;
   плюс `best.json` обязан содержать `objective` и `warnings`, а история — базовое измерение.
   Теперь страж нельзя отключить, не уронив гейт.

## Правила контура

1. Целевая функция и сплит сидов объявлены до измерения и не двигаются после.
2. Train и val не пересекаются: пересечение — исключение (`seedSplit`), а не предупреждение.
3. Значения — только из объявленной сетки: `loadParams` отвергает выход за диапазон
   и некратность шагу, поэтому «случайный поиск по непрерывному диапазону» невозможен.
4. История append-only. Отклонённый кандидат остаётся в `history.jsonl` — это данные
   о том, что проверено, а не мусор.
5. Если val хуже базового — тюнинг сам пишет `ВНИМАНИЕ: … это переобучение`, и набор
   не применяется без проверки человеком.
6. Прогон кандидата без evidence — ошибка (`нет evidence (exit=…)`), а не «ноль очков»:
   `run.mjs` возвращает 1 и при успешном прогоне без убийств, поэтому меряем по
   наличию доказательств, а не по коду возврата.
