# BRIDGE — агент и мир через шов `World`

Дата: 2026-09-18. Линия: `woof-ts`. Статус: **работает и проверен на живом env-сервере игры**.

## Зачем бридж

Агент обязан уметь играть в мир, который живёт **не в его процессе**: headless env-сервер
игры сегодня, авторитетный сервер (`:8787`, `/ws`) завтра. Поэтому вся политика стоит на
интерфейсе `World` (`src/world/world.ts`), а transports меняются под ним:

| Транспорт | Класс | Мир | Статус |
|---|---|---|---|
| `in-process` | `src/world/sim_world.ts` | `src/sim` игры в нашем процессе | рабочая лошадка: полный доступ к Sim, все привилегии объявлены |
| `ndjson-stdio` | `src/bridge/ndjson_bridge.ts` | `headless/env_server.ts` игры в отдельном процессе | **готов**, проверен на эквивалентность со стендом |
| `websocket` | — | авторитетный сервер игры (`:8787`, `/ws`) | следующий шаг; нужен клон `GAME_FULL=1` (добавляет `server/**`, `src/net/**`, `src/client/**`; `src/world_api/**` уже в базовом наборе) |

Политика одна и та же: `buildAgent(world, …)` (`src/core/build.ts`) собирает
память → FSM → арбитраж → исполнитель поверх любого `World`, а различия в том, что мир
показывает, объявлены в `capabilities` и печатаются **до прогона**.

## Собрать и запустить

```bash
bash tools/setup_game.sh      # клон игры (sparse) + зависимости + сборка агента
bash tools/build_env.sh       # env-сервер игры нашим esbuild → dist-env/env_server.cjs (6.8 МБ)
node dist/run.mjs --transport ndjson --seed 42 --steps 120 --quiet
```

Env-сервер собирается **нашим** esbuild из дерева игры: `npm install` в игре тянет весь
фронтенд (vite/react), а серверу нужны только `src/sim` + `headless`. Дерево игры при этом
не изменяется — артефакт лежит в нашем `dist-env/`.

## Контракт upstream (взят из `headless/env_server.ts`, не придуман)

```
-> {"cmd":"info"}                                            <- {"obs_size","num_actions","actions"}
-> {"cmd":"reset","seed":N,"player_class":"warrior","config":{...}}   <- {"obs":[...],"info":{...}}
-> {"cmd":"step","action":N}                                 <- {"obs","reward","terminated","truncated","info"}
-> {"cmd":"close"}                                           (ответа не обещано — ждать строку нельзя)
info = {level, xp, hp, kills, deaths, quests_done, copper, step}
```

Один запрос — ровно одна строка ответа. Ошибки приходят как `{"error":"…"}` и
превращаются в исключение вместе с хвостом stderr мира (глушить stderr, как это делает
python-клиент upstream, — значит потерять причину падения).

Размеры **спрашиваем** у мира и сверяем с фактами игры: `obs_size`/`num_actions`/словарь
действий обязаны совпасть с `gameFacts()`, иначе прогон падает до первого измерения
(«мир не тот, за кого себя выдаёт»).

## Что видно по проводу и чего не видно

Раскладка obs выводится из фактов игры (`src/bridge/obs.ts`, `obsLayout()`):
`self(16) | abilities(2×48) | target(9) | nearest mobs(6×5) | interactable(5) |
quests(2×224) | paladin(3)` = 607. Смещения не захардкожены: если upstream изменит
баланс, `obsLayout` упадёт на сверке с `obsSize()`.

| Что | По проводу | Как используем |
|---|---|---|
| координаты игрока | ✅ `x/WORLD_MAX_X`, z-нормаль | восстанавливаем абсолютно (границы мира — из данных игры), точность float64 |
| уровень, HP, xp | ✅ `info.hp`, `obs.level/MAX_LEVEL` | `maxHp` выводим как `hp / hpFrac` (на первом кадре точно) |
| способности | ✅ готовность и кулдаун по слотам | имена слотов — из `abilitiesKnownAt` (тот же источник, что у `sim.known`) |
| цель | ✅ доля HP, Δуровня, дистанция, пеленг, hostile/lootable/агро | `target` |
| ближайшие мобы | ✅ до 5 живых враждебных в 60 ярдах: дистанция, пеленг, доля HP, Δуровня, агро | `nearby`; пустой слот = дистанция 60 |
| труп/объект/NPC | ⚠️ **один** ближайший в `INTERACT_RANGE` | `corpses`/`objects`/`npcs` (0 или 1 элемент) |
| квесты | ✅ состояние и доля выполнения каждого | `active`/`ready`/`done` точны; **ноль неразличим** между `available` и `none/failed` → возвращаем `other` |
| счётчики | ✅ kills, deaths, quests_done, copper, level, xp, step | `counters`; `levelUps` выводим из уровня |
| id сущностей | ❌ | `entityIdentity='slot'`: id синтетические отрицательные, личность между кадрами не сохраняется |
| вид сущности (`templateId`) | ❌ | `entityTemplates=false`: бой решаем по наблюдаемой Δуровня (`canFightObservedLevel`), а не по данным контента |
| абсолютное HP сущностей | ❌ | `entityAbsoluteHp=false`: `hp` = доля, `maxHp` = 1 |
| накопленный урон | ❌ | `damageCounters=false`: `counters.damageDealt/Taken = 0`, а успех боя определяется по **наблюдаемой доле HP цели** (`FARM_HP:…`) |
| содержимое сумок | ❌ | `itemCountApi=false`: `countItem()` бросает исключение |
| счётчики по каждой цели квеста | ❌ | `questObjectiveCounts=false`: для одноцельных квестов `have` выводится из доли точно, для многоцельных `have=0` (консервативно «нужно всё») |

Отдельно: **кто такой NPC рядом** — по проводу не отдаётся. Мы определяем его по слою
карты (статические пины из контент-данных игры) и восстановленным координатам игрока:
ближайший пин в пределах `INTERACT_RANGE`. Это вывод из наблюдения и данных клиента,
а не чтение чужой памяти.

Кандидаты на выдачу квеста за бриджем — проходимые квесты NPC, которые не `done` и не
`active`. Факт выдачи проверяется `interact`-ом и последующей сверкой (`ACCEPT` /
`ACCEPT_FAILED`), а не угадывается: состояние `available` по проводу неразличимо.

## Синхронный канал (почему воркер и `Atomics`)

Интерфейс `World` синхронный, а мир за бриджем — процесс с асинхронным stdin/stdout.
Читать pipe синхронно в Node нельзя: libuv переводит pipe в неблокирующий режим, и
`fs.readSync` отдаёт `EAGAIN` (проверено). Поэтому:

- процессом мира владеет **воркер** (`src/bridge/sync_channel.ts`, код воркера — строка
  с `eval: true`, чтобы переживать сборку в один бандл);
- обмен идёт через `SharedArrayBuffer`: воркер кладёт строку ответа в общий буфер,
  ставит флаг и делает `Atomics.notify`; основной поток спит на `Atomics.wait`;
- смерть процесса и переполнение буфера будят ждущего **по тому же индексу**, иначе
  ожидание висело бы до таймаута;
- stderr мира копится в общем буфере и попадает в текст исключения;
- замер: ~0.17 мс на круг (3001 запрос за 503 мс) — на порядки быстрее env-сервера.

Ловушка, которая стоила времени: `Buffer.from(typedArray, offset, length)` **игнорирует**
offset/length и копирует весь view — нужен `subarray`.

## Проверено (тесты и прогоны)

`tests/bridge_env.test.ts` — 15 тестов на **живом** процессе env-сервера:

- раскладка obs выводится из фактов и сходится с `obsSize()`; obs другой длины — исключение;
- `info` возвращает те же размеры и тот же словарь действий, что и дерево игры;
- действие вне словаря — отказ мира, а не тихий `noop`; после `close` мир не отвечает;
- **эквивалентность со стендом**: тот же сид и та же последовательность из 25 действий
  дают совпадающие kills/deaths/quests_done, HP, координаты, число и дистанции ближайших
  мобов, готовность и кулдауны способностей (точность 1e-4…1e-6);
- честность ограничений: `questState('q_wolves')` = `other` у бриджа при `available` у
  стенда; `countItem` бросает; id сущностей отрицательные; `templateId` пустой, а не
  выдуманный; `damageDealt` = 0 при живом уроне на стенде.

Живой прогон (`--transport ndjson --seed 42 --steps 120`):

```
[WoOF] транспорт: ndjson-бридж к dist-env/env_server.cjs
[WoOF] мир: транспорт=ndjson-stdio, … состояние квестов=observed, идентичность сущностей=slot,
       вид сущностей (templateId)=нет, абсолютное HP сущностей=нет
[WoOF] мир: счётчики урона=нет (0, не используется как сигнал), …
[Agent] SUMMARY steps=120 world_steps=5530 kills=2 deaths=0 quests_done=1 first_turn_in_step=6
[WoOF] ПРОГОН СОСТОЯЛСЯ: есть настоящие убийства
```

Цепочка за бриджем: дойти по пину карты к Drillmaster Hale → `ACCEPT:q_hub_know_your_numbers`
→ 10 ударов по манекену (`FARM_OBJ … 60 → 100`) → `TURN_IN` на шаге 6 → дальше бой с
мобами по наблюдаемой Δуровня.

Для сравнения, стенд на том же сиде и 150 решениях: `4323 / 24 / 22 / 2 / шаг 12`.
Разрыв в убийствах объясним и объявлен: стенд видит всех живых сущностей в 60 ярдах
(включая NPC) и знает вид моба, а за бриджем NPC виден только в 5 ярдах и вид моба
неизвестен. `world_steps` в обеих строках — одна единица (шаги мира = действия × frameSkip).

## Что найдено благодаря бриджу (исправлено в политике, а не в бридже)

1. `canFightMob(templateId, …)` возвращал `false` для пустого `templateId` → за бриджем
   агент не дрался вовсе. Добавлено `canFightObservedLevel(Δуровня)`; выбор правила —
   по объявленной возможности `entityTemplates` (`ArbitrationLayer.fightable`).
2. Успех боя определялся по накопленному урону, которого по проводу нет → любой бой без
   убийства выглядел как `FARM_FAILED`, и навык вставал на перерыв. Добавлена проверка по
   **наблюдаемой** доле HP цели (`FARM_HP:…`); работает в обоих транспортах.
3. Порядок выбора пина квестодателя: при неизвестной доступности квестов приоритет по типу
   цели уводил агента мимо ближайшего NPC к дальнему «kill-квесту». За бриджем
   (`questStateApi='observed'`) идём к ближайшему пину и проверяем `interact`-ом.
4. Провалы выдачи квеста ничему не учили: агент долбил NPC с закрытым по классу квестом.
   Добавлен порог `giverFailExhaust` (по умолчанию 3) — после трёх `ACCEPT_FAILED` подряд
   NPC вычёркивается (`GIVER_EXHAUSTED:…`). Работает и на стенде (там была та же болезнь:
   34 прибытия к Hale).
